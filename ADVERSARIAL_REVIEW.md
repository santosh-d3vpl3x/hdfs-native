### 3. **High** — AM resync bookkeeping: `AllocateState` corrupts pending counts on concurrent ask updates, capability changes, and back-to-back failovers
* **Locations:** [am.rs](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L204-L219), [am.rs](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L244-L249), [am.rs](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L309-L335), [am.rs](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L469-L503), [am.rs](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L540-L556)
* **Defects vs. Java Hadoop (even when `allocation_request_id` is explicitly `Some(id)`):**
  1. **Wrong deduction order when updating an ask in the same heartbeat a container arrives:** On the RM (`DefaultAMSProcessor.allocate` -> `LocalityAppPlacementAllocator.updatePendingAsk`), containers returned in `AllocateResponse` were already deducted by the scheduler *before* the incoming `AllocateRequest` overwrites the RM's pending ask count to `N` — so after the RPC, the RM still holds `N` pending containers. In `AmRmClient::allocate` ([am.rs:470-502](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L470-L502)), `state.add_request` sets `self.asks[K].num_containers = N` first and `state.on_response` then calls `remove_satisfied_asks` on the containers returned by that heartbeat, decrementing `self.asks[K]` to `N - allocated.len()`.
  2. **`AskKey` includes `capability` unlike YARN 3's `SchedulerRequestKey`:** In Hadoop 3 (`AppSchedulingInfo` + `LocalityAppPlacementAllocator`), the RM keys `ResourceRequest`s by `(priority, allocationRequestId)` -> `resourceName` (without `capability`). Changing `capability` (or cancelling with `Resource::default()` and `num_containers = 0`) at the same `(priority, allocation_request_id, resource_name)` replaces the request on the RM, but leaves the previous `(priority, resource_name, old_capability, allocation_request_id)` entry alive in `AllocateState.asks` ([am.rs:204-209](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L204-L209)).
  3. **Single-shot resync in `allocate` and `unregister_application_master`:** Unlike Java's `AMRMClientImpl.allocate` and `unregisterApplicationMaster` (which loop/recurse on `ApplicationMasterNotRegisteredException`), [am.rs:477-484](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L477-L484) and [am.rs:549-553](file:///root/workspace/hdfs-native/rust/yarn-native/src/am.rs#L549-L553) only resync once per call (`reregistered = true`).
* **Concrete failure:**
  * AM asks for `num_containers = 2` (`allocation_request_id = Some(1)`) in Heartbeat 1. The RM allocates `C1` (RM pending = 1). In Heartbeat 2, AM updates its request to `num_containers = 2`; RM sets pending = 2 and returns `C1`, while `AmRmClient` decrements `self.asks` to `1`. After RM failover, `resend_all()` asks for `1` instead of `2`, under-allocating and hanging the job.
  * If AM resizes `(priority=1, allocation_request_id=Some(1), "*")` from `1024 MB` to `2048 MB` and RM fails over, `resend_all()` sends both in `HashMap` iteration order, nondeterministically overwriting the `2048 MB` ask with the stale `1024 MB` ask on the RM.

* **Defects vs. Java Hadoop:**
  1. **No failover on mid-call crash for `@Idempotent` operations:** In Java Hadoop (`ApplicationClientProtocol.java`, `ApplicationBaseProtocol.java`, `RetryPolicies.FailoverOnNetworkExceptionRetry`), `submitApplication`, `forceKillApplication`, `moveApplicationAcrossQueues`, `updateApplicationPriority`, `getDelegationToken`, `renewDelegationToken`, and `cancelDelegationToken` are `@Idempotent` (and `ApplicationMasterService.finishApplicationMaster` is deduplicated via `isAppFinalStateStored()` / `finishedAttemptCache`), so Java fails over to `rm1` on post-send `EOFException` / `SocketException` / `SocketTimeoutException`. `yarn-native` (and `hdfs-native` for token RPCs) marks all of them `write = true`, so [proxy.rs:352](file:///root/workspace/hdfs-native/rust/yarn-native/src/proxy.rs#L352) (`write && !is_safe_write_failover_error`) aborts immediately on `UnexpectedEof`, `ConnectionReset`, `ConnectionAborted`, or `TimedOut` after sending the request.
  2. **HA `max_attempts` counts individual proxy hops instead of full rings:** In [config.rs:206](file:///root/workspace/hdfs-native/rust/yarn-native/src/config.rs#L206) and [config.rs:278-282](file:///root/workspace/hdfs-native/rust/yarn-native/src/config.rs#L278-L282), setting `yarn.resourcemanager.connect.max-wait.ms` smaller than the retry interval (e.g. `0` for fail-fast, or `1000` with default `30000` interval) yields `max_attempts = 0`. In [proxy.rs:355](file:///root/workspace/hdfs-native/rust/yarn-native/src/proxy.rs#L355), `failovers >= self.failover.max_attempts` triggers on the very first `StandbyException` from `rm0` (`0 >= 0`) **before `rm1` is ever tried once**.
